# B3 — הפרדת שכבות: שינוי, בדיקות וראיות

## מצב ונקודת התחלה

**המימוש, האימות ושילוב תיעוד ההגשה הושלמו; אושר קומיט מקומי ללא push.** נקודת ההתחלה השמורה היא 0ddf6a2 (B2), ללא שינויים מקומיים. נוצר ענף מקומי codex/b3-layers; לא בוצעו commit/push. המקורות המדויקים שנבדקו חתומים ב-[B3-test-run.json](evidence/B3-test-run.json). אין שינוי תלויות, סכמת מסד או Angular.

לפני השינוי עברו 83 בדיקות שרת ב-2026-09-09 17:19:52 +03:00 (`.local-run/b3-baseline.log`). לאחר השינוי עברו 86 ב-17:23:47, אפס כישלונות, שגיאות ודילוגים (`.local-run/b3-after.log`). כל 83 הבדיקות הקודמות נשמרו במשמעותן; הותאמו רק בניית ה-Controller וחיבור השירות האמיתי לבדיקות. נוספו שלושה מבחנים לסיכוני השינוי.

## דרישה מפורשת והיקף

README דורש הפרדת אחריות מה-Controller ללא over-engineering. הסיכונים הנגזרים מכך: שמירת API/JSON, מיקום כללי המכסה, טרנזקציות, שאילתות והתנהגות B1/B2. SQL injection היה ממצא ידוע מראש; תיקון קשירת הפרמטר מתועד בנפרד כבונוס אבטחה ולא כבאג מכסה חדש.

| רכיב | לפני | אחרי והנימוק |
|---|---|---|

| LeaveRequestService — חדש | היצירה והרשימה היו ב-Controller | יצירה ובדיקות קלט/מכסה, טרנזקציית יצירה; קריאות רשימה וחיפוש ב-readOnly. שירות קונקרטי אחד ללא ממשק ריק |

תקינות תאריכים ושדות נבדקת לפני גישה למסד בשירות היצירה כדי להגן גם על קריאה שאינה HTTP. המרת JSON/טיפוסים נשארת בגבול HTTP. השירות מחזיר Entity או CreationException עם Failure עסקי; ה-Controller בלבד ממפה כשל יצירה ל-400/404 וגוף הטקסט הקיים. חוזה חריגות האישור הקיים נשמר כדי לא להרחיב את B3 לשכתוב נוסף. לא נוספו DTOs חדשים, mapper, שירות בסיס גנרי או טיפול שגיאות גלובלי.

create נכנס דרך Spring לטרנזקציה, ו-getAll/search לקריאה readOnly. האישור נשאר בטרנזקציה עצמאית דרך שירות האישור; אין קריאה פנימית באותו אובייקט שעוקפת proxy. סדר נעילת העובד, קריאת בקשה וניצול, שמירה ו-commit לא השתנה. יצירה אינה שומרת מכסה ל-PENDING; גם אחרי השינוי רק אישור צורך אותה.

## תקלות וסיבת שורש

- אבטחה, לפני התיקון: GET search עם הקלט `') OR TRUE --` החזיר 200 ו-17 רשומות במקום 0; ראיה ב-R/securityBefore. SQL חובר בקוד Controller עם שרשור ישיר. לאחר העברה ל-Repository וקישור :name כנתון, אותו קלט מחזיר רשימה ריקה ב-HTTP ובבדיקת PostgreSQL. שמות עם גרש פועלים, wildcard אחוז/קו תחתון נשאר לפי LIKE המקורי. זה תיקון SQL injection בנקודת החיפוש בלבד, לא ביקורת אבטחה מלאה.
- אריזה ראשונה נכשלה כי תהליך Java הישן 21836 נעל את ה-JAR ב-Windows (`.local-run/b3-package.log`). נתיב התהליך אומת לפני עצירתו. אריזה חוזרת עברה ב-17:25:52 (`.local-run/b3-package-retry.log`), והשרת החדש 27664 הופעל מאותו JAR. אין שינוי קוד בעקבות הכשל ואין שינוי נתוני מסד. hash ה-JAR ב-R.
- לא נכשלו בדיקות עסקיות בסבב. לא הוחלשו assertions ולא בוצעו דילוגים. הוספת שירות אינה טענה לבאג B1 חדש.

## בדיקת עשן ידנית ומה משתנה במסך

אין שינוי חזותי מתוכנן. המסך ב-http://localhost:4200 וה-Swagger ב-http://localhost:5080/swagger-ui.html. הבדיקות הזמינות בוצעו על ידי הסוכן; הנתונים נשארו לשחזור.

עובד 6: B3 O'Brien QA 20260909-172621. בקשה 18 היא 18 ימים מאושרים;19 היא 2 ימים מאושרים;20 היאיום ממתין;21 היאמחלה של יום מאושרת. ב-GET /api/leave-requests וברענון המסך יש לראות 19/21 Approved ו-20 Pending. POST /api/leave-requests/19/approve יחזיר 409 (כבר אושר), ו-/20/approve יחזיר 409 (אין יתרה). יצירה חדשה של VACATION לעובד 6 תידחה לאחר מיצוי 20 הימים. ליצירה/אישור תקין חוזר אפשר ליצור SICK ליום חדש דרך API ולהשתמש במזהה המוחזר; זוהי הוראת שחזור ולא טענה שיצירה נוספת זו בוצעה.

מקרים של יתרה מדויקת והצלחה לפני מיצוי הוכחו ב-H וב-Testcontainers. אין לאפס את העובד לשחזור; אין צורך לממש F1–F3 כדי לסגור B3.

## תיעוד ושמירה
